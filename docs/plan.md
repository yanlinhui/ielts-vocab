# 雅思词汇真经 · 项目计划

> 本文档是项目的推进主文档。**方案变动时同步更新这里**，不要让它和代码脱节。
> 最后更新：2026-10-16

---

## 1. 项目目标

把《雅思词汇真经(刘洪波)》这本纸质书，变成一个**能每天真正用起来**的背单词网页工具。

「真正用起来」的定义——必须满足这三条，否则就是玩具：

1. **有复习计划**：不是"看一遍"，而是系统知道每个词你什么时候该再见一次
2. **有检验手段**：能检验你是真记住了还是只是眼熟（拼写/听写）
3. **有进度反馈**：能看到自己背了多少、哪些词老忘、坚持了多少天

### 3.4 两个被排除的方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 我自己读扫描图 | **不可行** | Read 工具对每页都返回 `[Unsupported Image]`，拿不到图像内容 |
| 用你转的 Word 文档 | **用不上** | 没有文字层（`document.xml` 只有 2 段版权信息）；分辨率 3.54 MP，**比 PDF 的 5.78 MP 低 39%**；还少了 12 页 |

**2026-10-15 追加调整：学习卡片背面改成全展开**

原设计的背面是四个默认折叠的 `<details>`（例句/搭配/词根/文化背景），要挨个点开。改成**一次性全铺开**，并给卡片加了高度约束：单词和评分按钮钉在上下两头。理由和实现坑记在 `tech-spec.md` 5.5，页面规格同步改在 `PRD.md` 2.2。

**翻面保留**——去掉它等于把「回忆测试」降级成「阅读理解」。用户 2026-10-15 明确选了「保留翻面，背面全展开」。

**2026-10-15 再调整：去掉正文滚动，改字号自适应**

第一版是「卡片锁一屏 + 中间正文自己滚」。用户反馈：翻面后还得上下滑才看得全，不行——要的是一屏全显。

实测数据支持这个诉求：3580 个词里 3395 个只有 1 条例句、69 个没有例句，**正文中位数才 136 个字符**。也就是说 96% 的词本来就够一屏，是那把高度锁把它们拘住了。

改成：正文不再滚，内容放不下时**逐档缩小正文字号**（17px 起，最小 11px），缩到底仍放不下才轮到滚动条兜底。实测桌面和手机尺寸下，`lithosphere` 这类短词字号完全不变、卡片完整落在视口内、页面不滚动、评分按钮可见；注入 500 字长内容后字号自动降到 14.8px，仍然一屏全显。

代价：约 1.5% 的长词（53 个）字会小一号。这是「一屏全显」唯一可能的实现方式——内容不会凭空变短。

**踩到的坑**：一开始想按卡片当前高度算可用高度，不行——卡片是按内容撑开的，字号一缩小卡片跟着变矮，"可用高度"也跟着缩，于是字号一路缩到最小档还觉得放不下（`lithosphere` 只有一条例句，第一版实测被缩到了 11px）。改成按 `max-height` 上限算，这个坑暂时绕过去了，但那只是把问题挪了个地方——2026-10-16 发现它还有第二个坑，见下。

**2026-10-16 追加：矮窗口下会溢出，已修**

实测复现：在 613×586 的窗口里，头部 101px + 底部 101px 吃掉卡片的 56%，正文只剩 160px，字号被压到最小档 11px **仍然溢出 85px**、出现滚动条——和「一屏全显」的承诺不符。

改了三处，**只动 `WordCard.tsx`**（不动页面容器，避开 `StudySession` 和 `RatingButtons`）：

1. `max-height` 的预留从 `14rem` 收到 `11rem`——它要覆盖卡片外的导航栏、进度条、退出链接等开销，14rem 记得过于保守
2. 矮窗口（`max-height: 44rem`）走一套紧凑尺寸：头部/底部内边距收窄、单词小一号、区块间距从 `1.6em` 收到 `1em`、卡片下方那行键盘提示隐藏
3. **字号自适应的判据从「和估算的可用高度比」改成「直接量有没有溢出」**——同时要求"正文没在自己的框里溢出"和"页面没被卡片顶出滚动条"

同样内容的效果：

| 视口 | 改前 | 改后 |
|---|---|---|
| 375×812（手机） | 15.98px | **17px** |
| 1280×720（笔记本） | 13.6px | **17px** |
| 613×586（矮窗口） | 11.22px **+ 溢出 85px** | **17px**，不溢出 |
| 613×586 + 330 字长词源 | 溢出 + 滚动条 | **13.6px**，不溢出 |

原理和三个判据为什么都不能用，见 `tech-spec.md` 5.5。

**2026-10-16 再追加：整页还是会滚，已修**

> ⚠️ **本节这一整套「一屏全显」方案在同一天被推翻**，见下面「方向反转」一节。保留下来的原因是它记了两个真实踩过的坑（估算值必估错、判据要用实测溢出量），思路本身没错，错的是目标。

上一版把「整页不滚」押在 `max-height: calc(100dvh - 11rem)` 上，那个 `11rem` 是估的。实测它在哪都估小——卡片外开销 271px 宽时 225px、375px 宽时 195px，`11rem`（176px）都不够，于是整页被顶出滚动条：用户得往下滑才看得见底部的评分按钮，正是「一屏全显」要消灭的东西。

改成不再估算任何东西：

1. **解除卡片的人工限高**，让它按内容自然撑开——正文因此恒不溢出，「有没有溢出」只剩判整页一条
2. **逐档试字号**，取第一个「整页不出现滚动条」的档位
3. 所有档位都装不下时，把卡片**限高到「页面刚好不滚」**，溢出量由 `scrollHeight - innerHeight` 得来，全程不碰估算值

同时把矮屏那套紧凑尺寸再收紧一档（单词 `2xl→xl`、音标 `sm→xs`、卡片左右内边距 `6→4`、评分按钮 `py-3→py-2`、正文区块间距 `1.6em→0.65em`、释义行高 `1.6→1.45`、例句块内边距同步收）。改动只在 `WordCard.tsx` 和 `RatingButtons.tsx` 两个文件里。

| 视口 | 字号 | 整页滚动 | 卡片内滚动 |
|---|---|---|---|
| 1280×800 | 17px | 无 | 无 |
| 375×812 | 17px | 无 | 无 |
| 613×586 | 11.22px | 无 | 无 |
| 271×586 | 11.22px | 无 | 内容多的词会滚 |

**顺带修正了上一节表格里那个「613×586 → 17px」**：那是被 `max-height` 硬压出来的假象——卡片被限高后页面确实不滚，但卡片内的正文其实在滚。现在同一条件下真实的数字是 11.22px，是真的不滚。

最后一档是已知例外：271px 比 iPhone SE 还窄 100px，内容多的词（`mantle` 正文要 314px、卡片只给得出 184px）物理上装不下——要么砍区块、要么把字缩到不可读，两者都不划算。实际使用是大窗口，不追求这个尺寸。

顺带量化了一个此前只是定性的问题：**例句 13.4%（486/3635）存在 OCR 单词粘连**（`examinationcreated`）。见 `PRD.md` 第 4 节第 7 条。

**2026-10-16 方向反转：字号调大，卡片不再滚，改整页滚**

上面两节都在追「一屏全显」，代价全押在字号上——613×586 这类矮窗口下正文被压到 **11.22px**。用户实机用了几天后明确反馈：**字太小**，要求「卡片的滑动必须去掉，字号大了就整页滑」。

改动（`WordCard.tsx` + `globals.css` + `RatingButtons.tsx`）：

1. **删掉整套字号自适应**（`FIT_STEPS`、`fitContent`、`bodyRef` 和配套的 `resize` 监听），基准从 17px 提到 **18px**
2. **删掉全部矮窗口紧凑档**（`[@media(max-height:44rem)]` 的十几处覆写：单词 `3xl→xl`、音标 `sm→xs`、区块间距 `1.6em→0.65em`、行高 `1.6→1.45`、隐藏键盘提示等）
3. **正文块去掉 `overflow-y-auto` / `min-h-0 flex-1`**，卡片内不再有任何滚动区域
4. **补上翻面容器锁高**——删掉 `max-height` 后必须做：正反两面共用同一个 grid 单元格，行高取两者的较大值，不干预的话长词的背面会把空白的正面一起撑高，单词跑出屏幕、还没翻面就出现滚动条
5. **去掉 `perspective`**——有透视时近端半张卡被放大，实测量到翻转中途超出静止外框 9.96px，卡片的边会被削掉
6. **变矮延后半个翻转（210ms）**——翻回正面时立刻收矮会把还在转的背面下半截裁掉
7. 换词时页面滚回顶部

|---|---|---|---|---|

| 375×812 | 17px | **18px** | 无 | 0 / 215px |
| 613×586 | **11.22px** | **18px** | 无 | 206px |
| 注入 2000px 长内容 | — | 18px | 无 | 1406px（正面仍 320px） |

## 6. 版权（重要 · 已变更）

**自己背完全没问题**——自己的书，自己提取自己用。

**但要明确一点**：按 2026-10-15 的确认，MVP 会提取书里的 `[例]`例句、`[搭]`搭配、词根词源——**这些都是刘洪波与外研社的原创内容**，不是公开资料。

原计划里「释义用 ECDICT、不碰书中原文，所以版权上很干净」这个优势，**现在没有了**。

| 用途 | 风险 |
|---|---|
| 自己背 | 无。个人使用，合理。 |
| 分享给朋友（小范围、非公开） | 低，但严格说仍属未授权复制 |
| 公开部署（上线、发 GitHub） | **高**。等于公开传播受版权保护的原创内容 |

**结构上的应对（现在就做，成本为零）**：把书内原创内容（例句 / 搭配 / 词根词源）**单独存字段，不和基础词条混在一起**。真到公开那天，关掉这几个字段即可，数据库不用改。这也是数据模型里把例句拆成独立表的原因之一。

**⚠️ 一个实际存在的暴露点（阶段二发现）**

`.gitignore` 排除了 PDF（`*.pdf`）和页面图、OCR 中间产物，但 **`data/words.clean.json` 没有被排除，而它逐字包含书里的例句和搭配**。

- 当前是本地私有仓库，**没有风险**
- 但**若要公开这个仓库或把它推到 GitHub**，等于把这些原创内容一起公开了——和「公开部署」是同一种风险

到时候的处理（二选一）：
1. 把 `data/words.clean.json` 加进 `.gitignore`，只保留脚本和 docs；词库靠重跑流水线或在本地留存
2. 加一个导出脚本，生成「只含 ECDICT 字段、剥掉书内原创内容」的公开版词库

**在决定公开之前，这条不用动。**
